# Changelog

## Unreleased

- Milestone 0, repo scaffolding and CI: `package.json`, TypeScript build to `dist/`, a CLI stub that answers `--version` and `--help` and exits 2 on an unknown flag, tests with `node:test`, the text hygiene check (`scripts/check-text.mjs`), the pack smoke test (`scripts/pack-smoke.mjs`), an eval placeholder, the MIT license, and a CI workflow for Linux, Windows and macOS with Node 22 and 24.
- Milestone 1, normalized model and adapter interface: the normalized test model (`src/model/types.ts`) with its JSON Schema (`schemas/model.schema.json`), the language adapter interface and registry, the rule and report types, and capability gating: a rule runs on a file only when the file has every capability the rule requires, and a skipped rule is listed with the reason. A toy adapter in the tests proves the interface end to end without a parser. Adds the golden file test helper (`UPDATE_GOLDEN=1 npm test`).
- Milestone 2, tree-sitter runtime and grammars: the parser service (`web-tree-sitter`, WebAssembly, loaded on first use and cached), vendored grammars for JavaScript, TypeScript, TSX, Python and Java with a manifest (version, license, ABI, sha256) and their license texts, asset loading through `src/assets.ts`, 1-based positions on LF-normalized text, and the lexical scanner used as the fallback when a grammar is unavailable or more than 30% of a file is unparseable. Adds `docs/adapters.md` and `scripts/build-grammars.mjs`.
- Milestone 3a, config and glob helper: config loading from JSON or YAML (`qa-core-review.config.json`, `.yaml`, `.yml`, `.qa-core-review.json`, `.qa-core-review.yaml` or a `qa-core-review` key in `package.json`, searched from the root upward to the git root), `schemas/config.schema.json`, defaults for every key, and errors that name the file, the JSON pointer and the problem. YAML is parsed as plain data only: custom tags are rejected. Adds the glob helper (`**`, `*`, `?`, `{a,b}`, Windows-style input paths) and a byte order mark check in the text lint.
- Milestone 3b, project detection and discovery: the `detect` command (`--format pretty|json`, `--root`, `--config`) shows the projects found, their frameworks with the evidence for each, and the test files per adapter. Detection reads manifests only (`package.json` and runner config files, Python requirement and project files, `pom.xml` and Gradle build files) and never runs a build tool. In a monorepo each file belongs to the nearest project for its language, config `projects` entries override detection, and files in languages with no static adapter yet (Scala, Rust, Go and others) are listed under the generic adapter. An invalid config exits 2 with the file and the JSON pointer. Adds `schemas/detect.schema.json` and the fixture projects.
- Milestone 4a, JS/TS adapter structure: the `js` adapter reads tests, suites and hooks from JavaScript, TypeScript, JSX and TSX files for Playwright, Cypress, Jest, Vitest, Mocha, WebdriverIO and node:test. It extracts full titles, modifiers (`only`, `skip`, `fixme`, `todo`, `fail`, `concurrent`, `serial`), skips with their reason, `.each` tables and tests made in loops, 1-based spans, a body hash, imports and suppression comments, and it decides the runner of each file from its imports and globals before falling back to the project. Adds golden models for every framework and the shared adapter test helpers.
- Milestone 4b, JS/TS adapter assertions: the `js` adapter now reads what each test checks. It finds assertions written with `expect` (Jest, Vitest, Playwright, jest-dom, expect-webdriverio), Chai (`expect`, `should`, `assert`), node's `assert`, Sinon and Cypress `should`, with their kind, both operands (literal, locator, count, mock), and whether each one is negated, soft, finished, awaited, conditional or unreachable. It also reads `expect.assertions` guards, expected errors, `try`/`catch` blocks and promise `catch` handlers, and it counts calls to helper functions, page object methods and custom Cypress commands that contain an assertion. Adds `createHelperIndex` and the adapter's `collectHelpers`.
- Milestone 4c, JS/TS adapter body facts: the `js` adapter now also reads what each test does. It finds fixed sleeps and condition waits, selectors with their strategy and positional picks, steps, HTTP data operations, module, function and network mocks, the module under test, and the resources a test takes (spies, fake timers, globals, env values, browsers, contexts, pages) with whether they are released. A file that cannot be parsed is read by the lexical scanner, which still finds tests, focus and skip markers, assertions and sleeps. The adapter now fills every capability of the model. Adds `selectorStrategy` and the JS/TS section of `docs/adapters.md`.
- Milestone 5a, engine and `review` command: `qa-core-review review [paths...]` (also the default command) finds the test files, builds the helper index of each project, runs the rules each file supports and writes `.qa-core/review/report.json` (`schemas/report.schema.json`, version 2). Findings have a fingerprint with no line number in it, each test gets a verdict (pass, review or fail), and the exit code is 0, 1, 2 or 3 as documented. Flags: `--fail-on`, `--rules`, `--disable`, `--language`, `--framework`, `--format`, `--stdout json`, `--output`, `--dump-model`, `--root`, `--config`. The first rule is `QCR-X001` (a file that cannot be parsed, or a test file with no test in it). The text output is the summary only for now.
- Milestone 5b, text output and commands: `review` now prints the full text view: a header, one block per test (fail, then review, then pass) with each finding's rule, place, message, evidence and fix, then the findings about whole files, the summary and a line per language. New flags: `--quiet`, `--no-color` (also `NO_COLOR`), `--max-findings`. New commands: `rules`, `explain <ruleId>`, `adapters` and `init --config [json|yaml]`.
- Milestone 6, assertion rules: `QCR-A001` no-assertion, `QCR-A002` trivial-assertion, `QCR-A003` cannot-fail-assertion (not finished, never reached, not awaited, locator truthiness, a count of at least zero, a truthy list literal) and `QCR-A004` conditional-assertion, for JS/TS. Each finding has a fix and a good example in the language of the file, and `explain` prints the bad and good examples. `docs/rules.md` documents the rules. The helper index now also reads the local files a test file imports (two steps deep) and the Cypress support files, so a page object outside the test folders counts. Assertions have a new optional `operator` field for comparisons. A callback that calls `done()` or a promise's `resolve` no longer makes its assertions conditional. A supertest `.expect(...)` inside a request chain now counts as an assertion.
- Milestone 7, hard waits and brittle selectors: `QCR-W001` hard-wait reports a fixed sleep in a test or a hook (`waitForTimeout`, `cy.wait(2000)`, `browser.pause`, `await sleep(500)`, a promise that only a timer resolves), with the `maxMs` option, and a WebdriverIO implicit wait above 5000 ms as info. Waits for a condition, `cy.wait('@alias')` and fake clocks are not reported. `QCR-S001` brittle-selector reports an XPath that depends on layout, a selector that picks by position, a generated class or id, and a selector that follows 4 or more levels of page structure, with the `allowPatterns` option and the top-level `testIdAttribute`. Picks by position (`.nth(2)`, `.first()` on a plain selector) are info. The decision is made once for every language by the shared classifier `src/rules/selectors.ts`. Hooks in the model now have a `waits` list. A severity in the config sets the level of a rule, and a case the rule reports at a level of its own (info) keeps it. The config checks `maxMs` and `allowPatterns` when it loads.
- Milestone 8, swallowed errors, focused and skipped tests: `QCR-E001` swallowed-error reports an assertion in a `try` block or a promise chain whose handler catches the failure and goes on (`catch (e) { console.log(e) }`, `.catch(() => {})`, `.catch(console.error)`). A handler that throws again, fails the test or checks the error is fine, and so are soft assertions. `QCR-F001` focused-test reports `.only`, `fit`, `fdescribe` and `{ only: true }`. `QCR-F002` skipped-test reports a skip with no condition, a to-do, a fixme and a skipped suite, with the reason in the message when there is one. A skip on a condition is not reported, and an expected failure (`test.fail`, `it.failing`) is info. Hooks in the model now have a `selectors` list, so `QCR-S001` also reads a `beforeEach`. In the JS adapter, a `.catch(...)` handler is stored only when the tool can see what it does, a soft assertion is not counted as protected by a `try` block, and a Playwright group skip with a callback is no longer read as a test.
- Milestone 9, duplicates, snapshot-only tests and cleanup: `QCR-D001` duplicate-test reports every copy of a test body after the first, in one file or across files of the same language, and two tests with one title in a file. Parameterized tests and bodies under 2 statements are left out. `QCR-P001` snapshot-only reports a test whose only assertions are snapshots (warn) or visual checks (info), and an inline snapshot recorded empty. `QCR-C001` missing-cleanup reports fake timers, spies, environment variables, globals, browsers, contexts, pages and API clients that are never given back, in a test or a hook, with the `restoreMocksConfigured` option. A test that creates data over HTTP and never deletes it is info with low confidence. In the JS adapter, an after hook now releases resources only for its own suite and the suites inside it, and a spy stored through a chain of stub calls keeps its variable.
- Milestone 10, over-mocking and missing negative cases: `QCR-M001` over-mocking reports a mocked module under test and a stubbed function that the test calls and checks (both error), and a test that checks only calls on mocks, a file where every import is mocked, and a fake for every network request (all warn). The module under test comes from the file name or from the `subjectMap` option. A mock that keeps the real module (`importActual`, `requireActual`) is not reported. `QCR-N001` missing-negative-case reports, as info with low confidence, a suite or a file where every test is a happy path, with two or three cases to think about. `docs/rules.md` now has the full rule table with the qa-core-verify column and a support matrix made by `scripts/gen-support-matrix.mjs`, which `npm run lint` checks. Hooks in the model now have a `data` list, so `QCR-C001` sees what an after hook deletes. In the JS adapter, a mock function stored under a name is a function mock.
- Milestone 11, suppression and diff mode: a finding can be suppressed with a comment for the next line (`// qa-core-review-disable-next-line QCR-W001 -- reason`, or the same with `#`), with a comment before the first statement for the whole file (`qa-core-review-disable QCR-S001 -- reason`), or with a `suppressions` entry in the config (a file glob, the rules, an optional full test title and a reason). A reason is required: a comment with no reason is ignored and reported by the new rule `QCR-X002` suppression-without-reason (info). Suppressed findings get `suppressed: true`, are counted in `summary.suppressed`, appear only in the JSON report and never change a verdict or the exit code. `review --diff <base>` reviews only what changed since the branch left `<base>` (the merge base), plus changes that are not committed and files that are not tracked yet; `review --staged` reviews only what is staged. In both, a test is reported when one of its lines changed, a finding about a hook or a suite is reported when it sits on a changed line, and `QCR-F001` and `QCR-X001` are always reported in a changed file. The header of the text view names the base, and `mode.diffBase` in the report holds it (`staged` for `--staged`). Outside a git repository, with a base that git does not know, or with both flags, the command exits 2 with a clear message. `docs/rules.md` has a new section on suppressing a finding.
- Milestone 12, SARIF, Markdown and JUnit reports: `review --format` now takes `sarif`, `markdown` and `junit` next to `pretty` and `json`, and writes `report.sarif`, `report.md` and `report.junit.xml` into the output folder (`report.json` is always written). `--stdout sarif`, `--stdout markdown` and `--stdout junit` print one format for piping. The config key `output.formats` now takes effect, and the flag wins over it. With no `pretty` in the list, the command prints the summary line and the list of files in place of the text view. SARIF 2.1.0: one run, one `rules` entry per rule that ran with a link to its section of `docs/rules.md`, levels `error`, `warning` and `note`, paths relative to `%SRCROOT%`, the finding id as `partialFingerprints["qaCoreReview/v1"]`, and `properties` with the language, framework, test title and source. Markdown, for the PR comment: the marker line, a one-line verdict, a table of the tests that fail or need review (and of files with findings outside their tests), one collapsed block of findings per row, and a line that names files with no static adapter. Text from the code is escaped, and an `@name` in a test title mentions nobody. Over 60,000 characters the blocks are dropped and the table stays. JUnit XML: one suite per file, one case per test, a failure for each finding at or above `--fail-on` and the other findings in `system-out`, a `(file)` case for findings outside tests, and a skipped case for a file with no static adapter. Suppressed findings are in none of the three.
- Milestone 13a, Python adapter, structure: Python test files are now parsed (tree-sitter `python` grammar) into the normalized model. The adapter reads pytest and unittest: test functions and methods, classes as suites (`Test*` classes, `unittest.TestCase` subclasses of any name, and classes that extend one of those in the same file), setup and teardown functions and methods as hooks, `@pytest.fixture` functions as hooks with the code after `yield` as a `fixture-teardown` hook, skip and xfail marks and decorators (`pytest.mark.skip`, `skipif`, `xfail`, `unittest.skip`, `skipIf`, `skipUnless`, `expectedFailure`), `pytestmark` on a module or a class, skips inside a body (`pytest.skip`, `self.skipTest`, `raise unittest.SkipTest`, `pytest.importorskip`), parametrized tests (`pytest.mark.parametrize`, pytest-cases, `parameterized`, `subTest` loops), imports with their aliases, `#` suppression comments and the body hash. The runner of a file is pytest or unittest, with Playwright for Python and Selenium as libraries. The adapter declares only what it fills in so far (`tests`, `suites`, `hooks`, `modifiers`, `parameterized`, `body-hash`), so for Python files only `QCR-F001`, `QCR-F002`, `QCR-D001`, `QCR-X001` and `QCR-X002` run. The rules about assertions, waits, selectors, mocks and cleanup follow with the next parts of the adapter. `conftest.py` and `__init__.py` are support files.
- Milestone 13b, Python adapter, assertions: the adapter now reads what a Python test checks. `assert` statements (the kind comes from the expression: `==`, `is None`, `in`, a comparison, a bare value, `isinstance`), unittest `self.assert*` methods, `pytest.raises`, `pytest.warns` and `pytest.fail`, Playwright `expect(...)` with its matchers (awaited or not in the async API), mock assert methods, pytest-check soft checks, snapshot comparisons, PyHamcrest and assertpy `assert_that`, `raise_for_status()`, and any function named `assert_...`. Each assertion has its operands (literal, locator, count, mock), and whether it is negated, guarded, reachable and complete. A tuple assert, `pytest.raises(E)` as a bare statement, and mock look-alikes such as `send.called_once_with(1)` are recorded as assertions that check nothing. `try/except` blocks, `contextlib.suppress(...)` and `with pytest.raises(...)` are read as try blocks, with what they catch and what the handler does. Functions that hold an assertion are helpers, in the same file, in the modules a file imports and in `conftest.py`. The adapter now declares `assertions`, `assertion-operands`, `try-blocks`, `helpers` and `reachability`, so `QCR-A001` to `QCR-A004`, `QCR-E001`, `QCR-N001` and `QCR-P001` run on Python files. Importing `unittest.mock` no longer makes a pytest file count unittest as a library.
- Milestone 13c, Python adapter, what a test does: the adapter now reads what a Python test does besides checking. Waits: `time.sleep` and `asyncio.sleep` (seconds, stored as milliseconds), `wait_for_timeout`, Selenium `implicitly_wait`, condition waits (`wait_for_*`, `WebDriverWait(...).until(...)`) and fake time (freezegun, time-machine). Selectors: Playwright locators and `get_by_*` calls, page actions that take a selector, Selenium `By` strategies and the old `find_element_by_*` methods, with picks by position (`.first`, `.last`, `.nth(n)`, `find_elements(...)[i]`). Steps and test data: navigation, page actions, HTTP requests by verb and SQL by its first word. Mocks: `patch`, `patch.object`, `mocker.patch`, `mocker.spy`, `monkeypatch.setattr`, named `Mock` objects, Playwright `page.route` and the `responses`, `respx` and `requests_mock` libraries, with whether a mock has a fixed reply, keeps the real behavior, or answers every network request. A patched function is named the way the file calls it (`get_total` after `from shop.cart import get_total`). The module under test is found from the name of the test file or from `subjectMap`, and a patch replaces it when the file imports the patched name from it or calls it there. Resources: drivers, browsers, contexts, pages, files, connections, patchers started by hand and environment variables, each with whether it is released in the test, in a hook that covers it (`tearDown`, `teardown_*`, the code after a `yield`), by `addCleanup` or `addfinalizer`, by a `with` block, or by a pytest fixture that cleans up after itself. The adapter now declares every capability, so QCR-W001, QCR-S001, QCR-M001 and QCR-C001 run on Python files. When the grammar cannot be loaded or a file cannot be parsed, a lexical scanner still finds tests, unconditional skips, assertions and fixed sleeps, and the file is listed as `partial` with the four capabilities that the scanner fills. Python rule fixtures and Python fix texts come with Milestone 13d.
- Milestone 13d, Python adapter, rules and fix texts: every rule that applies to Python now has rule fixtures (29 folders under `fixtures/rules/<id>/python-<framework>/`, for pytest, unittest, Playwright and Selenium), and a finding in a Python file carries a Python example and, where the general fix names things Python does not have, a fix in Python words. `explain <rule> --language python` prints them, and `docs/rules.md` shows them next to the JS/TS examples with a short note per rule on what counts in Python. QCR-A003 has two more cases: a truth check that is given a second value (`self.assertTrue(total, 29.99)`), and a check on a mock that does not exist or is never called (`send.called_once_with(1)`, and in JS/TS `expect(send).toHaveBeenCalled` with no call, which was reported before as "never finished"). The message of QCR-E001 says "except block" in a Python file. Adapter changes that the fixtures showed were needed: a comparison handed to `assertTrue` or `assertFalse` is read as that comparison; a patch with no `return_value` counts as a fixed reply, because it still answers in place of the real code; `find_elements(...)[0]` is no longer a pick by position; what is made inside `with sync_playwright() as p:` is closed by that block; a helper that is handed to another call counts as a check inside a callback. This completes Milestone 13.
- Milestone 14a, Java adapter, structure: a first Java adapter (`src/adapters/java/`) reads the structure of JUnit 5, JUnit 4 and TestNG test files with the vendored tree-sitter grammar. It finds test methods (`@Test`, `@ParameterizedTest`, `@RepeatedTest`, `@TestFactory`, `@TestTemplate`, and the public methods of a TestNG class with `@Test` on it), classes as suites with `@Nested` and other inner classes as nested suites, `@DisplayName` titles, the hooks of the three frameworks (TestNG suite and test hooks have the scope `global`), skips (`@Disabled`, `@Ignore`, `@Test(enabled = false)` with its `description`), skips on a condition (the fourteen JUnit 5 condition annotations, `assumeTrue` and its relatives, a thrown `SkipException` or `TestAbortedException`), and parameterized tests with the number of cases where it is written out (`@ValueSource`, `@CsvSource`, the null and empty sources, a TestNG `@DataProvider` in the same class, the `@Parameters` method of a JUnit 4 `Parameterized` class). Names are found through imports of one class, of a whole package, of a static member, or by their full name. The runner of a file is the framework whose test annotation it names, so a TestNG test that uses the assertions of JUnit is a TestNG test. A base class with hooks in a support file is a suite of that file. A class that is named like a test class and whose test-shaped methods have no annotation stays a test file, so QCR-X001 says that no test was found in it. With these capabilities QCR-F001, QCR-F002, QCR-D001, QCR-X001 and QCR-X002 run on Java files. What a body checks and does comes with the next parts of Milestone 14.
- Milestone 14b, Java adapter, what a test checks: the Java adapter now reads the assertions of a test body, so QCR-A001, QCR-A002, QCR-A003, QCR-A004, QCR-E001, QCR-N001 and QCR-P001 run on Java files. It reads JUnit 5, JUnit 4 and TestNG assertions with the order of the values each one takes (JUnit takes the expected value first, JUnit 4 a message before it, TestNG the actual value first), a comparison inside `assertTrue`, `assertFalse` or an `assert` statement, AssertJ chains (one assertion per check; `assertThat(x)` with no check is not finished), the AssertJ checks on code that throws, Hamcrest matchers through `is` and `not`, the REST Assured checks after `.then()`, Spring `andExpect` and WebTestClient `expect...` checks, a Reactor `StepVerifier` (not finished when no `verify...` call runs it), Mockito `verify` and the BDD `then(mock).should()` (a `verify(mock)` that names no call is not finished), Playwright for Java `assertThat(locator)` matchers, ApprovalTests and snapshot checks, and methods named `assertSomething`. Soft assertions (AssertJ `SoftAssertions`, TestNG `SoftAssert`) are not finished when the test makes the object and never calls `assertAll()`. An expected exception is read from `assertThrows`, `@Test(expected = ...)`, `@Test(expectedExceptions = ...)` and the `ExpectedException` rule. Operands are marked as an element (Selenium `findElement`, `WebElement` variables, `@FindBy` fields, Playwright locators), a count (`size()`, `length`, `count()`) or a mock. An assertion is guarded under a condition, a loop that may run zero times or a callback that may not run, and not reached after an unconditional `return`, `throw`, `break`, `continue` or `fail`. A `try/catch` hides a failed assertion only when it catches `Throwable`, `Error`, `AssertionError` or one of the failure classes of JUnit: `catch (Exception e)` does not, because an assertion failure is an `Error` in Java. Methods that hold an assertion are helpers, in the test class or in a class of the project that the file imports or names. Waits, selectors, mocks, the class under test and resources come in the next part, so QCR-W001, QCR-S001, QCR-M001 and QCR-C001 do not run on Java files yet.
- Milestone 14c, Java adapter, what a test does: the Java adapter now reads waits, selectors, mocks and resources, so every rule runs on Java files. QCR-W001, QCR-S001, QCR-M001 and QCR-C001 are new for Java. Waits: `Thread.sleep`, `TimeUnit.X.sleep`, `Uninterruptibles.sleepUninterruptibly`, Selenide `sleep` and Playwright `waitForTimeout` are fixed sleeps, in milliseconds whatever unit they are written in (`Duration.ofSeconds(2)`, `2, TimeUnit.SECONDS`). `implicitlyWait(...)` is an implicit wait setting. `WebDriverWait` and `FluentWait` `.until(...)`, Awaitility and the Playwright `waitFor...` calls are waits for a condition. Selectors: Selenium `By.xpath`, `By.cssSelector` and the other `By` methods, `@FindBy` fields (also `how = How.XPATH, using = ...`), Playwright `locator`, `getBy...` and page actions with a selector, Selenide `$`, `$$`, `$x`, and picks by position (`.nth(2)`, `.first()`, `findElements(...).get(2)`). Mocks: Mockito `@Mock`, `@Spy`, `@MockBean` and the newer Spring names, `mock(X.class)`, `spy(x)`, `mockStatic`, and the replies `when(...).thenReturn(...)`, `doReturn(...).when(...)` and the BDD forms. A spy keeps the real behavior until it is given a reply. WireMock `stubFor(...)` and Playwright `page.route(...)` are network fakes. The class under test comes from `subjectMap`, from the `@InjectMocks` field, or from the name of the test file when the file names that class (`CartTest` tests `Cart`). A `@Mock` of the class under test is QCR-M001, an error. Resources: `new ChromeDriver()` and the other drivers (Appium too), `WebDriverManager...create()`, Playwright `Playwright.create()`, `launch()`, `newContext()` and `newPage()`, `System.setProperty`, `mockStatic` outside a try-with-resources, JDBC connections, `WireMockServer` and `MockWebServer`. A resource is released in the same body, in an after hook of its class or of a class around it, or by a try-with-resources. The hooks of a base class are joined to the classes that extend it, so a driver that `BaseTest` quits is not reported as a leak in `LoginTest extends BaseTest`. Data: REST Assured requests, Spring `RestTemplate`, HTTP clients by their name, SQL through JDBC, and `save` and `delete` on a repository. Selenide `shouldHave(...)` and `shouldBe(...)` and WireMock `verify(...)` are read as assertions. A Java file that cannot be parsed is read by the lexical scanner, which still finds the test methods, skips, assertion lines and fixed sleeps.
- Milestone 23, CI templates and pre-commit: `init --ci <provider>` writes a ready pipeline file for GitHub Actions (`.github/workflows/qa-core-review.yml`), GitLab CI (`.gitlab-ci.yml`), Azure Pipelines (`azure-pipelines.yml`), Jenkins (`Jenkinsfile`) or Bitbucket Pipelines (`bitbucket-pipelines.yml`) from `templates/ci/`. Each one fetches the git history, reviews what the pull request changes (`--diff`), writes the JSON, SARIF, Markdown and JUnit reports, hands the findings to the CI system in the form it shows natively, and fails the job on errors. A pipeline file that is already there is never changed: the template is printed to copy from, and a second run does nothing. `--force` replaces only the GitHub workflow, the one file that belongs to this tool alone. `init --pre-commit` adds the hook to `.pre-commit-config.yaml` for the pre-commit framework: it writes the file, or adds the entry at the end of the `repos` list and checks that nothing else changed, or prints the lines when the file cannot be changed safely. New `.pre-commit-hooks.yaml` with two hooks, `qa-core-review` (Node) and `qa-core-review-docker` (the Docker image). `templates/precommit/` also has a Husky script and a Lefthook snippet that run `npx qa-core-review --staged`. `init` with `--ci` or `--pre-commit` alone no longer writes a config file. New `docs/ci.md` with numbered steps for each CI system and each hook. Every template names the version of the package it ships with, and a test fails when one does not, so release prep cannot miss one.
